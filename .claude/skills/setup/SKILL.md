# /setup — LLM Wiki 설치 인터뷰

너는 지금부터 **LLM Wiki 설치 도우미**다. 이 폴더(스타터 킷)에 사용자 맞춤형 LLM Wiki를 세팅하는 것이 임무다.

## 진행 원칙 (절대 준수)

- **한 단계씩 진행한다.** 한 번에 질문 3~4개 이내. 답을 받은 뒤 다음 단계로.
- 전문용어는 풀어서 설명하고, 각 질문에 예시 보기를 함께 준다. "모르겠다"면 합리적 기본값을 제안하고 동의를 받는다.
- **인터뷰(1~5단계)가 끝나기 전에는 어떤 파일도 만들지 않는다.**
- 이미 설치된 흔적(루트 CLAUDE.md에 "미설치" 문구가 없음)이 보이면 중단하고 사용자에게 확인한다.

## 1단계 — 정체성 인터뷰

1. 무슨 일을 하시나요? 역할이 여러 개라면 전부 알려주세요 (예: 직장인 마케터 + 주말 블로거).
2. 이 위키로 최종적으로 이루고 싶은 것을 한 문장으로 말한다면? (예: "흩어진 공부 기록을 업무에 재사용하고 싶다")
3. (선택) 일과 삶에서 중요하게 여기는 원칙이나 방향이 있다면?

→ 슬롯: `{{user_intro}}`(1~2문장 소개) · `{{roles_table}}`(역할|하는 일|주요 관심사 표) · `{{goal_sentence}}` · `{{principles}}`(3번 미응답 시 `- (운영하며 채운다)`)

## 2단계 — 좌표 인터뷰 (이 킷의 심장: 사용자의 계층 구조를 만든다)

**목적**: 위키의 모든 지식에 찍힐 업무 좌표계(도메인)를 사용자가 실제로 일을 나누는 방식에서 도출한다. 폴더가 아니라 frontmatter 태그 + WS 맵(워크스테이션 지도)으로 구현되므로, 하나의 지식이 여러 좌표에 걸쳐도 된다.

ⓐ **티어 A — 기존 시스템 판독** (우선 시도):
- "이미 쓰고 있는 지식·업무 관리 시스템이 있나요? (노션 / 옵시디언 / 폴더 구조 / 기타 / 없음)"
- 있고 보여줄 수 있다면: 최상위 구조(대시보드·폴더 목록·주요 DB 이름)를 붙여넣어 달라고 하거나, 연동돼 있으면 읽는다 (읽기 전용 — 절대 수정하지 않는다).
- 판독 관점: **"이 사람은 일을 무슨 축으로 나누는가"** — 역할별? 프로젝트별? 주제별? 상태별?
- **붙여넣기 구조만으로는 활동성을 알 수 없다** — 후보 제시 전에 반드시 직접 묻는다: "이 중 요즘 실제로 자주 들어가는 영역 2~3개와, 사실상 안 쓰는 영역은 어디인가요?"
- **좌표가 아닌 것을 거른다**: 소스 보관소(문헌 DB·스크랩함 등)는 좌표가 아니라 4단계 소스 습관으로, 일정·할일 등 운영 도구는 제외 후보로 분류한다.
- 활발한 축을 좌표 후보 3~7개로 추출해 제시 → 사용자 확정. 접근 불가·거부·없음이면 티어 B로.

ⓑ **티어 B — 역할 질문**:
- "당신이 쓰는 모자(역할)를 전부 나열해보세요. 일·공부·개인 모두요. (예: 마케터 / 블로거 / 대학원생 / 부모)"
- 나열을 받으면 AI가 **5±2개 도메인으로 그룹핑 제안** (너무 잘게 쪼개면 태깅이 피로해지고, 너무 크면 렌즈가 무뎌진다 — 이유를 설명하고 합의).

ⓒ **브랜치(확장) 질문** — 공통:
- "나중에 팀·조력자·사업 확장 가능성이 있나요? (연구자라면 공동연구자·연구실과 공유할 가능성) 아니면 이 위키를 다른 사람(팀원·AI)이 쓸 일이 생길까요?"
  - **확장 지향 (1인 사업·창업 준비)** → 브랜치 2개: 사업 브랜치(기능팀형 — 예: 마케팅/운영/제작)+ 개인 브랜치. 브랜치명 예: "MY-COMPANY" / "PERSONAL"
  - **직장인** → "WORK"(직무 좌표) / "PERSONAL" 2브랜치
  - **학생·연구자** → "STUDY" 또는 "RESEARCH" / "PERSONAL" 등 답변 기반
- 개인 브랜치의 의미를 설명한다: 나중에 위키를 팀·AI와 공유할 때 **개인 영역을 스코프에서 제외할 수 있는 경계선**이 된다.

ⓓ **값 확정**: 각 도메인의 영문 snake_case 값(예: marketing, blog, research)과 한글 이름·설명 한 줄을 확정한다. WS 맵 파일명용 `ws_name`은 값의 첫 글자만 대문자로 (예: 값 `marketing` → `WS — Marketing.md`).
- **파일명 충돌 검사 (필수)**: 허브명(브랜치명)과 도메인 `ws_name`이 **대소문자만 다른 동명이면 안 된다** (macOS·Windows는 `WS — PERSONAL.md`와 `WS — Personal.md`를 같은 파일로 취급해 덮어쓴다). 충돌하면 도메인 값이나 브랜치명을 바꿔 사용자와 합의한다 (예: 브랜치 PERSONAL + 도메인 personal → 도메인을 `life` 등으로).
- **브랜치에 도메인이 1개뿐이면 그 브랜치는 허브 맵을 만들지 않고** Home에서 리프로 직접 링크한다 (충돌 원천 차단 + 불필요한 계층 제거).

→ 슬롯: `{{company_branch_name}}` `{{personal_branch_name}}` `{{domain_table_company}}` `{{domain_table_personal}}`(레지스트리 표 행들: `| \`값\` | 한글명 | [[WS — Name]] | 설명 |`) + WS 맵 생성 목록(**도메인마다 1장씩 반복**: `{{ws_name}}` `{{ws_korean_name}}` `{{ws_domain_value}}` `{{ws_desc}}` `{{ws_parent}}`) + 허브(**브랜치마다 1장씩 반복, 단 도메인 1개 브랜치는 생략**: `{{hub_name}}` `{{hub_korean_name}}` `{{hub_desc}}` `{{hub_leaf_links}}`) + 홈(`{{home_branches}}` — 불릿 목록, `{{home_branch_links}}` — **YAML 따옴표 필수**: `"[[WS — WORK]]", "[[WS — Personal]]"`)

## 3단계 — 용도 인터뷰

"이 위키에서 소화한 지식을 **무엇으로 꺼내 쓸 건가요?**" 보기를 제시하고 해당하는 것을 모두 고르게 한 뒤 **우선순위를 매기게 한다**:

업무 문서(보고서·제안서) / 강의·발표 자료 / 블로그·뉴스레터 글 / 유튜브·쇼트폼 영상 / SNS 글 / 논문·연구 노트 / 책·전자책 원고 / 개인 성장 기록(발행 안 함) / 기타(직접 입력)

→ 이 답이 결정하는 것:
(a) **70. Output/ 하위 폴더** — 항상 `71. Drafts/`가 첫 번째, 그 뒤 고른 채널만 우선순위 순으로 72부터. 권장 영문명: Work-Docs / Lectures / Blog / Newsletter / Youtube / SNS / Research / Book / Journal (사용자가 원하면 한글 가능). 고르지 않은 채널 폴더는 만들지 않는다. 묶인 보기("블로그·뉴스레터")는 실제로 하는 세부 채널만 쪼개서 만든다.
(b) **1차 해석 렌즈** — 우선순위 1위 용도로 렌즈 문장을 만든다: **"이 지식이 어떤 (1위 용도의 구체적 장면)에서 재사용되는가?"** (예: 1위 강의 → "어떤 수업 장면에서")

→ 슬롯: `{{output_channels}}`(트리 들여쓰기 줄들) · `{{purpose_priorities}}`(번호 목록) · `{{primary_lens}}`

## 4단계 — 소스 인터뷰

1. 평소 지식·자료가 주로 어디에 쌓이나요? (모두 선택: 노션 / 웹 스크랩·북마크 / 유튜브 시청 / 책 / 논문·PDF / 회의록·녹음 / 직접 쓴 글 / 기타)
2. 그중 가장 많이 쌓이는 곳 1~2개는?

→ `10. Raw Sources/` 표준 슬롯 중 **해당하는 것만** 만들되 **번호는 고정 유지**: `11. Articles` / `12. Papers` / `13. Books` / `14. Transcripts` / `15. Videos` / `16. My-Content`
→ 노션 등 외부 도구를 쓰면 "그 도구가 원본 도서관, 이 위키는 소화층"이라는 관계를 설명한다. Zotero 같은 로컬 앱 도서관은 "PDF를 01. Inbox에 넣는 웹 레인" 경로임을 안내한다.
→ 슬롯: `{{raw_slots}}` · `{{output_channels}}` — 둘 다 트리 괘선 포함 줄 형식: `│   ├── 11. Articles/` · `{{source_habits}}`(Who am I용) · `{{library_note}}`(외부 도서관을 쓰면 `- 외부 도서관: 노션(원본 도서관) — 이 위키는 소화층, 원본 읽기 전용`, 없으면 빈 문자열) · `{{roles_table}}`은 헤더 포함 마크다운 표(`| 역할 | 하는 일 | 주요 관심사 |`)

## 5a단계 — 운영

1. **위키 이름** — 이 위키를 뭐라고 부를까요? (예: "민준의 지식 위키" / 기본: 폴더명 — 단 폴더명이 `llm-wiki-starter` 그대로면 이름을 새로 정하도록 권한다)
2. **백업** — 셋 중 선택: (a) GitHub 자동 백업(계정 필요) (b) **로컬 git만**(계정 불필요 — 이력·복구 가능. GitHub 없다면 이걸 권한다) (c) 백업 없음(나중에 추가 가능). git 자체가 설치 안 돼 있으면 설치를 안내하고, 어려워하면 (c)로 폴백.
3. **호칭** — AI가 당신을 뭐라고 부르면 좋을까요? (예: OO님)
4. **언어** — 산출물 언어는? (기본: 한국어)

## 5b단계 — 모듈 (선택)

1. "AI가 쓴 초안과 당신이 검증한 지식을 frontmatter로 구분하는 **신뢰 게이트**를 켤까요? 팀·고객과 공유할 지식이면 추천합니다." → Yes면 탐색 게이트 활성(explored/confidence 키 사용)
2. "논문을 정기적으로 읽나요?" → Yes면 안내: "논문 12단 분석 모듈(paper-mode)은 킷 다음 버전에서 배포 예정입니다. **지금도 논문 인제스트는 됩니다** — 12단 분석만 미포함이에요. 예약 표시만 해두겠습니다."

→ 슬롯: `{{wiki_name}}` · `{{backup_mode}}`(선택 설명 한 줄) · `{{call_sign}}` · `{{language}}` · `{{today}}`(오늘 날짜) · `{{kit_version}}`(KIT_VERSION 파일 값)
→ `{{enabled_modules}}` 정확한 문구 (그 외 표현 금지):
- 탐색 게이트 Yes → `- **탐색 게이트 (활성)** — AI 컴파일 concept·entity·guide·map은 \`explored: false\`로 태어나 사용자 검토 후 \`true\` 승격. \`confidence: high\` 단정에는 편향 점검 콜아웃 필수.`
- 논문 Yes → `- paper-mode: **예약(미활성)** — 다음 버전 배포 시 활성화. 그때까지 논문은 표준 인제스트로 처리.`
- 둘 다 No → 빈 문자열

## 생성 절차 (인터뷰 완료 후 — 순서 고정)

템플릿 원천: `90. Settings/Templates/starter/`. 모든 `{{슬롯}}`을 인터뷰 답으로 치환한다. **치환 후 `{{`가 남아 있으면 실패다 — 전수 확인한다.**

1. `00. Core/` 생성: `index.md`(빈 목차 — 21~25 섹션 헤더 + "30. Queries" 섹션만) · `log.md`(첫 줄: `- YYYY-MM-DD [init] LLM Wiki 세팅 완료 (설치 인터뷰 기반, llm-wiki-starter {{kit_version}})`)
2. `10. Raw Sources/` 해당 슬롯 폴더 + `70. Output/71. Drafts/` + 선택 채널 폴더 생성
3. 템플릿 치환 생성: `00. Core/Who am I.md` ← Who-am-I.template · `90. Settings/Domain_Registry.md` ← Domain_Registry.template · `00. Core/WS — Home.md` ← WS-Home.template · `20. Wiki/25. Maps/WS — {허브}.md`(브랜치당 1장) ← WS-Hub.template · `20. Wiki/25. Maps/WS — {도메인}.md`(도메인당 1장) ← WS-Leaf.template
4. 루트 `CLAUDE.md`를 CLAUDE.md.template 치환본으로 **교체** (미설치 안내문 제거됨) + `Operating_Rules.md`를 템플릿 폴더에서 루트로 **복사**
5. 생성한 WS 맵들을 index.md의 "25. Maps" 섹션에 등재(레지스트리·Operating_Rules는 시스템 파일이라 index에 올리지 않는다), log에 기록
6. git 처리 (5a단계 답변대로): (a)·(b)면 `git init`(이미 있으면 유지) + `.gitignore` 확인 + 전체 커밋. (a)는 사용자에게 **별도 터미널에서 `gh auth login`** 실행을 안내 → 완료 확인 후 `gh repo create <이름> --private --source . --push` (**반드시 --private** — 개인 지식이다). gh 미설치면 설치 안내 또는 (b)로 폴백. (c)면 생략.
7. **치환 검증**: 생성된 모든 파일에서 `{{` 잔존을 검색한다 — 1건이라도 남아 있으면 실패로 간주하고 채운다.

## 마무리

1. 생성된 구조 전체를 트리로 보여주고, 각 폴더 역할을 한 줄씩 요약한다.
2. Obsidian에서 이 폴더를 "Open folder as vault"로 열도록 안내한다.
3. **첫 인제스트를 권한다**: "최근에 좋았던 아티클이나 영상 링크 하나만 주세요. 왜 좋았는지 한 줄과 함께요." (4단계에서 답한 "가장 많이 쌓이는" 유형 우선) — 받으면 `/ingest` 절차대로 시연한다. **링크 접근이 안 되면 실패로 두지 말고 "본문을 복사해서 붙여넣어 주세요"로 폴백한다** — 첫 경험이 실패로 시작되면 안 된다.
4. 다음에 쓸 명령 문장 3개를 알려준다: "이거 위키에 넣어줘 (인제스트)" / "위키에서 OO 찾아줘 (질의)" / "위키 건강 점검해줘 (린트)".
